# پایه عملیاتی ERP: احراز هویت و ساختار سازمانی

این شاخه نخستین قابلیت عمودی قابل اجرا را به مخزن اضافه می‌کند. این پیاده‌سازی یک **محیط توسعه/آزمایش** است و هنوز به حساب Cloudflare وصل یا منتشر نشده است.

## محدوده فعلی

- Cloudflare Worker با APIهای `/api/health`، `/api/v1/auth/status`، `/api/v1/auth/bootstrap`، `/api/v1/auth/login`، `/api/v1/auth/logout`، `/api/v1/auth/me` و `/api/v1/org-units`.
- D1 migration برای کاربران، نقش‌ها، نشست‌ها، تلاش‌های ورود، واحدهای سازمانی و رویدادهای ممیزی.
- راه‌اندازی یک‌باره مدیر اولیه با Secret سمت سرور؛ رمز عبور با PBKDF2-HMAC-SHA256 و salt تصادفی هش می‌شود.
- نشست تصادفی ۲۵۶ بیتی؛ فقط SHA-256 توکن نشست در D1 ذخیره می‌شود. Cookie دارای HttpOnly، Secure، SameSite=Strict و Max-Age است.
- محدودسازی تلاش‌های ناموفق ورود بر اساس کلید هش‌شده ایمیل/IP، کنترل نقش سمت سرور، کنترل مبدأ، اعتبارسنجی payload و ثبت ممیزی.
- رابط فارسی RTL واکنش‌گرا برای bootstrap/login، مشاهده واحدهای سازمانی و ایجاد شرکت/سایت/واحد/سمت/خط تولید/انبار.

## تنظیم محیط توسعه

1. Node.js 22 یا جدیدتر لازم است.
2. یک D1 جداگانه برای توسعه بساز؛ دیتابیس `erp-connectivity-test-20261028` فقط برای آزمون اتصال است و نباید برای داده ERP استفاده شود.
3. شناسه معتبر محلی `00000000-0000-4000-8000-000000000001` در `wrangler.toml` فقط برای D1 محلی است. برای D1 راه‌دور، شناسه دیتابیس توسعه اختصاصی واقعی را جایگزین کن.
4. در فایل محلی `.dev.vars` (که Git آن را نادیده می‌گیرد) مقدار `BOOTSTRAP_SECRET` را به‌عنوان یک رشته تصادفی محرمانه با حداقل ۳۲ نویسه تعریف کن. آن را در کد یا GitHub commit نکن.
5. `npx wrangler d1 migrations apply erp-dev --local` برای D1 محلی؛ `npx wrangler dev` برای اجرا.
6. آزمون‌های مستقل: `npm test` و `npm run check`.

برای D1 راه‌دور، ابتدا یک دیتابیس توسعه جداگانه و شناسه آن را بساز و پس از بازبینی تنظیمات، migration را فقط روی همان منبع آزمایشی اجرا کن. این شاخه به‌صورت خودکار به دیتابیس راه‌دور یا Production وصل نمی‌شود. هرگز شناسه placeholder را منتشر نکن.

## قرارداد API

- همه پاسخ‌های API JSON هستند و خطاها ساختار `{ error: { code, message } }` دارند.
- bootstrap: `POST /api/v1/auth/bootstrap` با هدر `X-Bootstrap-Secret` و فیلدهای `email`، `display_name` و `password`. فقط یک مدیر اولیه پذیرفته می‌شود.
- login: `POST /api/v1/auth/login` با `email` و `password`; نشست از طریق Cookie امن بازگردانده می‌شود.
- logout: `POST /api/v1/auth/logout`; نشست revoke و رویداد ممیزی ثبت می‌شود.
- هویت فعلی: `GET /api/v1/auth/me`.
- فهرست واحدها: `GET /api/v1/org-units` (نیازمند نشست).
- ایجاد واحد: `POST /api/v1/org-units` (فقط نقش admin)، با `code`، `name`، `unit_type` و `parent_id` اختیاری برای شرکت.
- ساختار والد محدود است: سایت زیر شرکت؛ واحد زیر شرکت/سایت/واحد؛ سمت زیر واحد؛ خط تولید زیر سایت/واحد؛ انبار زیر سایت.
- `GET /api/health` وضعیت اتصال D1 را برمی‌گرداند.

## معیارهای پذیرفته‌شده در این شاخه

پذیرش به نتیجه CI وابسته است: مهاجرت روی SQLite واقعی تست اجرا شود؛ ورود/خروج و نشست، bootstrap یک‌باره، کنترل دسترسی، ثبت شرکت، جلوگیری از کد تکراری، اعتبارسنجی ساختار والد و مبدأ غیرمجاز آزموده شوند. این هنوز جایگزین آزمون بار، بازبینی امنیت مستقل، MFA، بازیابی رمز، تأیید ایمیل، مدیریت کاربران/نقش‌ها از UI یا CRUD کامل سازمانی نیست.

## مرزهای عملیاتی

هیچ Worker منتشر نشده، هیچ دیتابیس راه‌دور migrate نشده و هیچ Secret/Production تنظیم نشده است. شناسه D1 در فایل فعلی عمداً placeholder است. برای اتصال GitHub Actions به Cloudflare باید workflow اتصال PR #1 دستی اجرا شود؛ در این نشست ابزار dispatch دستی Workflow در دسترس نیست، بنابراین مقدار Secretهای GitHub یا مجوز مؤثر آن‌ها را نمی‌توان از روی نامشان تأیید کرد.
