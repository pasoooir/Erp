# سامانه ERP کارخانه خودروسازی

> **دستورالعمل اصلی برای هر ChatGPT، عامل کدنویسی یا توسعه‌دهنده‌ای که این مخزن را باز می‌کند:** پیش از شروع کار، این README، ساختار واقعی مخزن، آزمون‌ها، گردش‌کارهای CI، [گانت پروژه](./erp-project.json) و [داشبورد گانت](./Gonchar.html) را بررسی کن. این پروژه با توضیح و تولید کد پراکنده جلو نمی‌رود؛ هر تغییر باید یک مسئله واقعی را حل کند، با بخش‌های دیگر هماهنگ باشد و با آزمون و شواهد قابل بررسی شود. بدون نیاز به یادآوری دوباره از سوی کاربر، قواعد زیر را رعایت کن.

## ۱. سه منبع جدا اما به‌هم‌پیوسته

این سه مورد وظایف متفاوت دارند و **هیچ‌کدام جای دیگری را نمی‌گیرد**:

1. **گانت چارت (erp-project.json) — چه چیزی باید ساخته شود؟** نقشه نیازمندی‌ها، ساختار شش‌سطحی، معیارهای پذیرش اولیه و وابستگی‌های برنامه‌ریزی را نگه می‌دارد.
2. **GitHub Issues و Pull Requests — کار چگونه پیگیری و بازبینی می‌شود؟** کار اجرایی، محدوده تغییر، مسئول/فرایند، تصمیم‌ها، موانع، بازبینی و پیوند به تغییرات را ثبت می‌کنند.
3. **کد و آزمون‌ها — چه چیزی واقعاً پیاده‌سازی و تأیید شده است؟** منبع حقیقت برای رفتار واقعی سیستم‌اند. وجود یک ردیف در گانت، Issue، PR یا فایل کد به‌تنهایی اثبات نمی‌کند قابلیت کار می‌کند.

این سه باید از طریق **شناسه پایدار وظیفه گانت، Issue، PR/commit، مسیر فایل‌ها، آزمون‌ها و شواهد CI** به هم متصل شوند. پس از بررسی شواهد، وضعیت گانت به‌روزرسانی می‌شود؛ نه برعکس.

## ۲. مدل شش‌سطحی گانت

- **سطح ۱ — حوزه سازمانی:** دامنه کلان کسب‌وکار.
- **سطح ۲ — ماژول/زیرسامانه:** قابلیت‌های مرتبط در آن حوزه.
- **سطح ۳ — فرایند:** جریان کاری کسب‌وکار.
- **سطح ۴ — فعالیت/نیاز اجرایی:** مسئله یا نتیجه قابل آزمون.
- **سطح ۵ — بسته کاری فنی:** تفکیک معمول به داده و قواعد کسب‌وکار (DATA)، منطق سمت سرور/API (API)، رابط کاربری (UI)، و آزمون/امنیت/مستندات (QA).
- **سطح ۶ — وظیفه قابل واگذاری:** تغییر محدود و قابل پیگیری که باید فایل‌ها، معیار پذیرش، آزمون و شواهد مشخص داشته باشد.

شناسه‌های گانت باید پایدار بمانند؛ برای مثال، شناسه سطح ۶ را در عنوان یا بدنه Issue، توضیح PR و در صورت مناسب بودن پیام commit ذکر کن. از ایجاد هزاران Issue کم‌ارزش و تکراری خودداری کن: ابتدا کد و وابستگی‌های واقعی را بررسی کن، سپس وظایف معنادار را در بسته‌های کاری قابل بازبینی گروه‌بندی و به شناسه‌های گانت پیوند بده.

**توجه:** ساختار شش‌سطحی فعلی نقشه اولیه برنامه‌ریزی است، نه اثبات اینکه تمام جزئیات کسب‌وکار یا وابستگی‌ها نهایی و تأیید شده‌اند. نام‌های عمومی بسته‌های فنی و قواعد اولیه وابستگی باید با مخزن، مدل داده، API، آزمون‌ها و جریان واقعی کارخانه تطبیق داده شوند. اگر یک وظیفه فقط عنوان عمومی دارد، پیش از ادعای آمادگی برای اجرا، آن را با مسئله واقعی، محدوده، معیار پذیرش و آزمون دقیق‌تر کن.

## ۳. قرارداد ردیابی هر وظیفه اجرایی

برای هر وظیفه سطح ۶ که واقعاً وارد اجرا می‌شود، تا حد امکان این اطلاعات را ثبت کن:

- شناسه پایدار و مسیر کامل آن در گانت؛
- مسئله‌ای که حل می‌کند و نتیجه مورد انتظار برای کاربر/عملیات؛
- محدوده داخل و خارج کار؛
- پیش‌نیازها و دلیل وابستگی؛
- فایل‌ها، APIها، جداول/مهاجرت‌های داده و ماژول‌های مرتبط که **پس از بررسی کد واقعی** شناسایی شده‌اند؛
- معیارهای پذیرش دقیق و قابل آزمون؛
- آزمون‌های موفق، ورودی نامعتبر، مجوز/مستأجر غیرمجاز، خطاها و هم‌زمانی/idempotency در صورت مرتبط بودن؛
- پیوند Issue، PR و commit؛
- نتیجه اجرای آزمون/CI و شواهد قابل بازبینی؛
- وضعیت فعلی، مانع‌ها و تصمیم‌های باز.

موارد ناشناخته را حدس نزن؛ صریحاً «نیازمند بررسی» ثبت کن. مسیر فایل یا آزمونی را که وجود ندارد به‌عنوان شواهد واقعی معرفی نکن. هرچه از برنامه‌ریزی به اجرا می‌رسد باید قابلیت ردیابی روشن‌تری داشته باشد.

## ۴. قانون وضعیت و درصد پیشرفت — بدون ادعای بی‌مدرک

- **not_started:** کار شروع نشده است.
- **in_progress:** کار واقعاً شروع شده و تغییر یا بررسی قابل اشاره دارد.
- **blocked:** مانع مشخصی وجود دارد؛ مانع و اقدام بعدی را بنویس.
- **completed:** فقط زمانی مجاز است که معیارهای پذیرش بررسی شده، آزمون‌های مربوط اجرا و قبول شده، شواهد پیوند خورده و بازبینی لازم انجام شده باشد.

ایجاد Issue، نوشتن کد بدون آزمون، باز شدن PR یا سبز شدن یک آزمون نامرتبط، به‌تنهایی تکمیل نیست. اگر آزمون اجرا نشده یا شواهد ناقص است، کار را تکمیل‌شده علامت نزن. درصدها باید از کارهای واقعاً تأییدشده و معیارهای پذیرش به دست آیند؛ تعداد workflowها، فایل‌ها، Issueها یا خطوط کد معیار پیشرفت نیست. وضعیت والد فقط براساس وضعیت فرزندان و سیاست صریح پروژه محاسبه شود. همه درصدهای اولیه صفر هستند تا شواهد معتبر ثبت شود.

## ۵. روش اجرای کار برای ChatGPT و عامل‌های کدنویسی

بدون درخواست تأیید برای هر گام کوچک، چرخه زیر را به‌طور پیوسته انجام بده:

1. وضعیت واقعی مخزن، README، tracker، گانت، Issues/PRهای باز، شاخه‌ها، CI، کد، مهاجرت‌ها و آزمون‌ها را بررسی کن.
2. مسئله‌های واقعی و کارهای باقی‌مانده را از شواهد استخراج کن؛ فرض‌های گانت را با کد و فرایندهای واقعی اعتبارسنجی کن.
3. کارهای مستقل را موازی پیش ببر؛ برای فایل‌ها یا وابستگی‌های مشترک هماهنگی ایجاد کن و یک خطای CI را بهانه توقف همه ماژول‌های مستقل قرار نده.
4. برای هر بسته کاری اجرایی، ارتباط شناسه گانت ↔ Issue ↔ PR/commit ↔ فایل ↔ آزمون را برقرار کن.
5. تغییر کامل و منسجم را پیاده‌سازی کن؛ از mock یا داده نمایشی به‌جای قابلیت واقعی محصول استفاده نکن، مگر آنکه صریحاً برای آزمون باشد.
6. آزمون‌های مرتبط، typecheck/lint، بررسی امنیت و CI موجود را اجرا کن؛ خطاها را تا حد امکان رفع و دوباره اجرا کن.
7. تغییرات را بازبینی کن؛ سازگاری API و داده، مجوزها، tenant isolation، audit، اعتبارسنجی، خطاها و اثر بر ماژول‌های دیگر را بررسی کن.
8. شواهد را در Issue/PR و tracker ثبت کن و گانت را فقط مطابق نتایج تأییدشده به‌روزرسانی کن.
9. به کار بعدی برو و خلاصه‌ای از پیشرفت واقعی، آزمون‌ها، موانع و لینک شواهد ارائه کن. فقط در صورت نیاز واقعی به دسترسی، وابستگی بیرونی یا تصمیم کسب‌وکاری غیرقابل استنباط، مانع را شفاف اعلام کن.

### الزامات مهندسی و امنیتی

- معماری، فناوری، قراردادهای API و شیوه تست موجود را ابتدا از فایل‌های واقعی پروژه کشف کن؛ از تحمیل معماری فرضی خودداری کن.
- احراز هویت و مجوز را سمت سرور بررسی کن؛ داده‌های سازمان/مستأجر را از ورودی قابل دستکاری کاربر معتبر فرض نکن.
- رمز عبور پیش‌فرض یا مدیر ثابت نساز؛ فرایند امن راه‌اندازی مدیر اولیه و دعوت/ایجاد کاربر را رعایت کن.
- اسرار را در کد، log، مستندات یا خروجی آزمون قرار نده؛ اطلاعات حساس را ثبت نکن.
- عملیات مالی و موجودی را با اعتبارسنجی، audit، تراکنش/هم‌زمانی و idempotency متناسب محافظت کن؛ از حرکت تکراری دفتر موجودی و موجودی منفی غیرمجاز جلوگیری کن.
- تغییرات دیتابیس باید مهاجرت کنترل‌شده، سازگاری و آزمون داشته باشند؛ تغییر مخرب واقعی بدون تأیید ممنوع است.
- آزمون‌های منفی مجوز، جداسازی سازمانی، ورودی نامعتبر و خطاها را متناسب با هر قابلیت اضافه کن.
- UI باید به عملیات واقعی متصل باشد و حالت‌های بارگذاری، خالی، موفقیت، خطا و دسترسی غیرمجاز را مدیریت کند.

## ۶. ایمنی عملیات و مرز اختیار

**بدون تأیید صریح کاربر، این کارها را انجام نده:** ادغام نهایی در شاخه main، انتشار production، مهاجرت دیتابیس زنده، تغییر مخرب روی داده واقعی، یا تغییر/چرخش secrets و تنظیمات حساس. کار روی شاخه، ایجاد PR، آزمون محلی و محیط آزمایشی در محدوده دسترسی مجاز قابل انجام است. هرگز ادعا نکن deploy یا آزمونی موفق بوده مگر نتیجه واقعی آن را بررسی کرده باشی.

## ۸. معیار موفقیت پروژه

برای هر قابلیت باید بتوانیم به‌روشنی پاسخ دهیم:

1. چه مسئله واقعی را حل می‌کند؟
2. به چه داده‌ها، مجوزها، ماژول‌ها و فرایندهایی وابسته است؟
3. در کدام فایل‌ها/APIها/مهاجرت‌ها پیاده‌سازی شده است؟
4. چگونه و با کدام آزمون‌ها بررسی شده است؟
5. نتیجه CI و شواهد قابل بازبینی کجاست؟
6. کدام Issue/PR/commit و شناسه گانت آن را دنبال می‌کنند؟
7. چه چیزی باقی مانده یا مسدود است؟

**هدف، تولید بیشترین کد یا بیشترین تعداد وظیفه نیست؛ هدف، تحویل قابلیت‌های واقعی، یکپارچه، امن، آزموده‌شده و قابل ردیابی است.**


## پایه عملیاتی ERP (شاخه توسعه)

شاخه [`feature/erp-auth-org-units`](https://github.com/pasoooir/Erp/tree/feature/erp-auth-org-units) یک برش عمودی آزمایشی شامل Worker، دو D1 migration، ورود/نشست امن، bootstrap یک‌باره مدیر، ممیزی، مدیریت کاربران، نقش‌های RBAC و scope-based access برای ساختار سازمانی به‌همراه رابط فارسی RTL ارائه می‌کند. CI سبز [40717318032](https://github.com/pasoooir/Erp/actions/runs/40717318032) شامل ۱۳ آزمون Node و smoke با Wrangler/D1 محلی و Chromium است. راهنمای اجرا، API و محدودیت‌های باقی‌مانده در [`docs/ERP_FOUNDATION.md`](./docs/ERP_FOUNDATION.md) ثبت شده‌اند. این PR هنوز Draft است؛ هیچ Worker منتشر نشده و هیچ D1 راه‌دور یا Production تغییر نکرده است.


## قانون معماری اجباری: پوشه و نام‌گذاری اختصاصی هر ماژول

- هر ماژول/زیرماژول باید پوشه مستقل برای UI، منطق سمت سرور، آزمون‌ها و مستندات مربوط داشته باشد.
- از نام‌های مبهم و عمومی مثل `app.js`, `script.js`, `styles.css` یا `utils.js` برای فایل‌های ماژول‌ها استفاده نکن؛ نام فایل باید کاربرد و مالکیت آن را روشن کند.
- فایل‌های پوسته مشترک نیز نام توصیفی و مسیر مستقل دارند؛ مثال: `public/modules/erp-shell/erp-shell.js` و `erp-shell.css`.
- نمونه ماژول ورود: `public/modules/auth/login/login-form.html`, `login-form.css`, `login-form.js` و سرویس Worker در `src/modules/auth/login/login-handler.js`.
- هنگام انتقال فایل، تمام importها، مسیرهای Pages، تست‌ها، workflowها و مستندات را همان تغییر اصلاح کن؛ فایل قدیمی/تکراری بدون مصرف باقی نگذار.
- این قاعده برای تمام توسعه‌های بعدی و تمام گفتگوهای پروژه الزام‌آور است.


## معماری استقرار رایگان: GitHub Pages + Cloudflare Worker

- **Frontend:** فقط GitHub Pages از طریق workflow در `.github/workflows/deploy-pages.yml` و خروجی پوشه `public/` منتشر می‌شود. این workflow به Cloudflare Pages وابسته نیست.
- **Backend/API:** فقط Cloudflare Workers با ورودی `workers.js` و نام Worker برابر `erp-api` اجرا می‌شود؛ مسیرهای غیر `/api/*` از Worker سرویس داده نمی‌شوند.
- **منطق API:** پیاده‌سازی فعلی routeها در `src/index.js` و ماژول‌های زیر `src/modules/` نگهداری می‌شود؛ `workers.js` ورودی رسمی و مرز اجرای Cloudflare Worker است.
- **Database:** اتصال D1 فقط از binding سمت Worker با نام `DB` انجام می‌شود. مرورگر GitHub Pages هرگز مستقیماً به D1 دسترسی ندارد.
- **مبدأ مجاز مرورگر:** `APP_ORIGIN=https://pasoooir.github.io`؛ تنظیم CORS و کوکی‌های نشست باید با این جداسازی Frontend/API سازگار بمانند.
- **عدم استفاده از Cloudflare Pages:** فایل‌های Wrangler دیگر `assets` یا تنظیمات `previews` مخصوص Pages ندارند. برای انتشار رابط کاربری فقط GitHub Pages را استفاده کن.

برای انتشار Frontend، GitHub Actions باید از شاخه `main` پوشه `public/` را منتشر کند. برای Backend، انتشار Worker یک عملیات مستقل است و نباید در workflow مربوط به GitHub Pages ادغام شود. هرگونه انتشار production یا migration دیتابیس زنده همچنان نیازمند تأیید صریح مالک سامانه است.
